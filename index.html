proofscan

A command-line application flaw scanner. A finding is verified-exploitable only once a generated check changed another user’s data, and flips to fixed-verified only when that check no longer reproduces. There is nothing to deploy — this page is the walkthrough you can follow on a laptop, against fixtures, in an afternoon.

What it does

Most scanners hand you a pile of “maybe.” proofscan only promotes a finding when it has watched the other user’s data change. That is the whole product.

Four layers, cheapest first:

LayerWhat you get
1 · StaticBuilt-in AST rules, plus Semgrep / Gitleaks / Trivy when they are on PATH. Fast, no network. Coverage is printed before findings, so “scanner not installed” cannot look like “clean.”
2 · Reason + proveFlags likely authorisation-ordering defects, then stands up an ephemeral copy of your source and confirms by reading the victim’s state back — not by trusting the attacker’s status code.
3 · DynamicSame class of defect, from the outside, against a running instance you have authorised in writing. Gated in code, not in a warning.
4 · RemediateTicket + draft PR carrying the evidence. Re-runs the exact same check. Status becomes fixed-verified only when it no longer reproduces.

The flagship fixture bug is the reason the verifier does not trust HTTP status: the attacker receives 404 while the victim’s notes are still destroyed. A tool that believed the reply would call it safe and be exactly wrong.

When and where to use it

Use it when

  • A colleague shipped an internal Express app and asked you to “check it” before it goes anywhere. Afternoon review, source on disk.
  • You need a CI gate that fails on verified-exploitable, not on every linter nit.
  • You are doing first-pass due diligence on a Node service you are allowed to test, and you want evidence rather than a tool-generated opinion.
  • You want a GRC team to see what “prove the control” looks like on application security — the same thesis as proofplane.

Do not use it when

  • You do not have authorisation. Layer 3 will refuse without a complete authorisation record and --authorized. That is not a prompt you can click through.
  • The target is not yours to copy. Layer 2 runs a local process sandbox of source you already have. Treat it as you would running the project’s own tests.
  • You need a dashboard, a scheduler, or multi-repo orchestration. Those are wrappers you build around the CLI. The tool exits with a status code.
  • You want every class of bug. It goes deep on broken object-level authorisation and a small static rule set. It is not a “finds everything” scanner.

How to use it

Node 22+. No API key for the default path. The commands below are the ones you run against this repository’s fixtures — deliberately vulnerable sample apps that ship with the tool. That is how you learn it. Pointing Layer 3 at anything else requires a written authorisation record in targets.yaml.

1. Install and confirm the suite.

git clone https://github.com/RootCawsLLC/proofscan.git
cd proofscan
npm install
npm run build
npm test

The suite includes a clean fixture on which every rule must stay silent. That is the half of a scanner test suite that usually gets skipped, and it is the half that decides whether anyone will keep using the tool.

2. Layer 1 against the vulnerable fixture — static only, no network:

node dist/cli.js scan --path test/fixtures/repo/vulnerable

Read the coverage block first. ran, not_installed, no_input, failed, and skipped are different facts. Trivy against a project with no lockfile returns no results — not an error, just nothing. Reported as “0 dependency vulnerabilities,” that is a lie by omission. The coverage block exists so that lie cannot hide.

3. Layer 2 against the same fixture — reason, then prove, in a throwaway copy of that fixture:

node dist/cli.js scan --path test/fixtures/repo/vulnerable --layers static,ai-reasoning

The default reasoner is heuristic: deterministic, no network. A candidate is not reported as real on the reasoner’s word. Status stays unverified-flagged until the sandbox demonstrates a cross-user state change.

4. Acceptance checks — the documented path that clones the public FlaudeCode fixture and asserts expected findings:

npm run acceptance
npm run acceptance:phase2
npm run acceptance:agnostic
npm run acceptance:phase4

Layer 3 (acceptance:phase3) talks to a running fixture you started locally and is gated the same way a real target is. Do not point it at a system you have not been authorised to test.

5. After a verified finding, close the loop.

node dist/cli.js remediate --store test/fixtures/repo/vulnerable
node dist/cli.js reverify  --store test/fixtures/repo/vulnerable --fix <fixed-copy>
node dist/cli.js audit verify --store test/fixtures/repo/vulnerable

Exit codes: 0 clean (or below --fail-on), 1 a finding met the threshold (or a fix still reproduces), 2 refused or failed to run. That is what CI binds to.

Take it into your organization

  1. Start with Layer 1 in CI on repositories you own. Fail the build on --fail-on high or on verified-exploitable once Layer 2 is in the pipeline. Do not fail on every low-severity validation nit on day one — you will train people to ignore the gate.
  2. Treat coverage as a control metric. A pull request that drops Semgrep from ran to not_installed is a finding about the pipeline, not a clean scan.
  3. Layer 3 is a penetration-test activity. The authorisation record (authorized_by, authorized_at, authorization_basis, runtime_base_url) is the durable evidence of permission. The flag is a per-run confirmation. Both are required. Put the record in change-management, not in a Slack message.
  4. Do not attach a loss figure to a finding. A published breach study fills two nodes of a FAIR tree. A finding is a statement about one weakness in one codebase. Multiplying them invents a number with a citation and no measurement.
  5. Re-verify the fix with the same check. A ticket without a failing-then-passing re-run is a request, not a closed control. Layer 4 is that loop; the ticket sink ships as files so you can wire Jira or GitHub with your own credentials.

Playbooks — one-off review, enterprise wrapper, M&A, confirming a reported issue — are in docs/USE-CASES.md. The plain-language intro is docs/OVERVIEW.md.

Honest limits

verified-exploitable means one specific thing: a second synthetic identity performed the flagged mutation against the first user’s resource, and the first user’s stored data changed, in a faithful copy (or an authorised running instance). It is not a statement about your production topology. The default Layer 2 sandbox is a local process, not a container. Built-in rules are JavaScript/TypeScript and Express-shaped. A scanner that did not run is reported as such. The audit chain detects an edit, not a full rewrite. Full list: README · Honest limits.
